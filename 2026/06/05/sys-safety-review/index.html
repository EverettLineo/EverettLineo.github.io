软件与系统安全复习手册

基于课堂笔记、老师 PPT 与截图整理。用途：考前复习、框架梳理、问答题与综合题组织答案。
重点提示来自笔记：SQL 注入、XSS、模糊测试是综合题重点；缓冲区溢出、格式化字符串漏洞、Web 漏洞偏问答题；ROP、防护机制不足、进程内存空间结构、double free 也需要会简述。

0. 复习总框架

0.1 课程主线

软件与系统安全可以按一条攻击与防护链理解：

  1. 程序如何存在：进程、虚拟地址空间、段、页、ELF/PE、加载、链接、共享库。
  2. 数据如何被错误处理：缓冲区边界、整数范围、格式化字符串、SQL/HTML 解析。
  3. 漏洞如何形成：栈溢出、堆溢出、整数溢出、格式化字符串、SQL 注入、数组越界、double free、use-after-free、XSS、CSRF。
  4. 漏洞如何被利用：覆盖返回地址、破坏堆元数据、任意读写、控制流劫持、代码注入、代码重用、ROP。
  5. 防护为什么有效又为什么不充分：DEP/NX、canary、shadow stack、分离控制/数据栈、库升级、ASLR、过滤、预编译、权限控制、Fuzzing。
  6. 漏洞如何发现：文件 Fuzz、协议 Fuzz、Web Fuzz、XSS Fuzz、异常监控、崩溃分析。

0.2 考试复习优先级

第一优先级：SQL 注入、XSS、Fuzzing。需要能写流程、分类、例子、防御、局限。

第二优先级：缓冲区溢出，包括栈溢出、堆溢出、fastbin/unlink、DEP/canary/shadow stack/ASLR。

第三优先级：格式化字符串、整数溢出、数组越界、double free、use-after-free、ROP。

第四优先级：计算机存储空间原理。笔记标注为“非考试重点”，但它是理解漏洞的基础，问答题可能要求描述进程内存布局。

0.3 常用答题模板

定义题：先说“是什么”，再说“为什么会发生”，最后说“后果和防护”。

原理题：按“正常机制 -> 边界条件被破坏 -> 攻击者可控内容进入关键位置 -> 造成安全后果”组织。

防御题：按“输入验证/边界检查 -> 隔离和最小权限 -> 运行时检测 -> 编译器/系统机制 -> 防护局限”组织。

综合题：必须有例子。SQL 注入写登录/查询例子；XSS 写存储型/反射型/DOM 型；Fuzzing 写目标、输入、生成、执行、监控、分析。

1. 软件安全导论

1.1 软件安全与系统安全

软件安全关注软件在设计、实现、运行、部署中的安全性，特别是攻击者如何利用程序逻辑、内存管理、输入解析、权限控制等缺陷破坏保密性、完整性、可用性。

系统安全范围更大，包括软件安全、硬件安全、可信计算、操作系统安全机制、网络与数据安全等。课程中的软件漏洞往往依赖系统底层机制才能被理解，例如虚拟地址空间、栈帧、堆管理、动态链接库。

1.2 威胁与趋势

典型威胁包括：缓冲区溢出、格式化字符串、Web 漏洞、软件漏洞利用、操作系统安全机制绕过、漏洞实验与渗透测试。

现实意义：漏洞可能造成服务崩溃、权限提升、数据泄露、远程代码执行、蠕虫传播、0day 攻击。Morris 蠕虫、红色代码、Slammer 等历史案例说明，底层漏洞能在网络环境中快速扩大影响。

1.3 安全学习的基础

需要掌握：汇编、计算机组成原理、操作系统、C/C++ 内存模型、软件工程、软件测试、Web 基础、数据库基础。

课程强调的不只是“怎么攻击”，更重要的是理解漏洞为什么存在、防护机制为什么有边界，以及如何用测试和工程实践降低风险。

2. 计算机存储空间原理

2.1 进程与地址空间

进程是软件在操作系统中的基本运行形态。每个进程拥有相对独立的虚拟地址空间，保存代码、数据、堆、栈、共享库映射以及内核交互所需资源。

32 位系统的虚拟地址空间最大为 4GB。典型 Linux 布局中，用户空间大约为 0-3GB，内核空间大约为 3-4GB。每个进程的用户空间彼此独立，而内核空间由系统统一管理。

虚拟地址空间的意义：

  • 隔离：一个进程不能随意访问另一个进程的内存。
  • 简化编程：程序认为自己拥有连续地址空间。
  • 共享：相同共享库页面可以映射到多个进程。
  • 保护：页表和权限位控制可读、可写、可执行。

2.2 典型内存布局

从低地址到高地址，常见布局为：

  1. Code/Text 段：存放程序机器码，一般只读，可共享。
  2. Data 段：存放已初始化的全局变量、全局静态变量、局部静态变量，可读写。
  3. BSS 段：存放未初始化的全局变量和静态变量，程序加载时初始化为 0；不需要在可执行文件中保存具体初值，因此能减小文件体积。
  4. Heap 堆：动态分配区，由 malloc/free 等库函数管理，通常向高地址增长。
  5. Stack 栈：函数调用区，保存局部变量、参数、返回地址、保存的寄存器等，x86 上通常向低地址增长。
  6. 共享库/映射区：动态库、共享内存、mmap 区域等。

需要区分三组“堆/栈”概念：

  • 操作系统内存区域中的堆和栈：动态分配区与函数调用区。
  • 数据结构中的堆和栈：树形堆与后进先出栈。
  • 缓存层面说法中的堆栈差异：栈访问通常更局部、更快；堆生命周期复杂、碎片化更明显。

2.3 x86 与 IA-32 基础

x86 是 Intel 8086/8088 以来向后兼容的一系列指令集体系结构。IA-32 是 32 位 x86。x86-64 是兼容 x86 的 64 位扩展。

x86 主要特点：

  • CISC 复杂指令集：指令长度可变，操作码、前缀、ModR/M、SIB、位移、立即数共同决定指令含义。
  • 小端序：低位字节存放在低地址。
  • 常见运行模式：实模式、保护模式、系统管理模式。

小端序例子：数值 0x12345678 在低地址到高地址中依次存为 78 56 34 12。

2.4 x86 汇编基础：Intel 与 AT&T

PPT 中强调了 Intel 汇编与 Linux GNU 常见 AT&T 汇编的差异。读懂漏洞利用和栈帧示意时要能识别两种写法。

2863

[!note] 图意理解
老师这页 PPT 的目的不是要求死背所有汇编语法，而是提醒：同一条数据传送指令在两种汇编格式里，操作数方向、寄存器前缀、立即数前缀、寻址括号、宽度标记都不同。看栈帧、函数序言和 ROP gadget 时，必须先确认语法格式，否则容易把源操作数和目的操作数看反。

主要差异：

  • 大小写：Intel 常写 MOV，AT&T 常写 movl。
  • 操作数方向：Intel 通常是“目的操作数在左，源操作数在右”，如 MOV EAX, EBX 表示把 EBX 送入 EAX；AT&T 通常是“源在左，目的在右”，如 movl %ebx, %eax。
  • 前缀：AT&T 中寄存器加 %，立即数加 $；Intel 通常不加。
  • 间接寻址：Intel 使用 []，AT&T 使用 ()。
  • 后缀：AT&T 用指令后缀表示操作数宽度，b 表示 byte，w 表示 word，l 表示 long；Intel 常用 BYTE/WORD/DWORD 等显式说明。

示例对照：

含义 Intel AT&T
把 EBX 放入 EAX MOV EAX, EBX movl %ebx, %eax
立即数 MOV EAX, 1 movl $1, %eax
内存间接寻址 [eax] (%eax)

理解这些差异有助于看懂函数序言、push/mov/sub 建栈过程、ret 返回过程和 ROP gadget。

2.5 分段、分页与地址翻译

IA-32 保护模式下的内存管理可理解为：分段是必需机制，分页是可选但现代系统普遍使用的机制。

[!note] 图意理解
这张 PPT 图说明 IA-32 的分段模型：程序给出的逻辑地址由段选择器和偏移组成，段机制把它转换为线性地址。这里的重点是“应用看到的地址”和“CPU/MMU 最终访问的地址”不是同一个层次。

地址转换链路：

  1. 程序使用逻辑地址，逻辑地址由段选择器与偏移量组成。
  2. CPU 根据段机制转换为线性地址。
  3. MMU 根据页表把线性/虚拟地址转换为物理地址。
  4. 物理地址送往内存。

[!note] 图意理解

分页机制通过页目录、页表、页内偏移完成映射。笔记中提到 PGD、PUD、PMD、PTE，含义分别是多级页表中的页全局目录、页上级目录、页中间目录、页表项。页内偏移用于定位页内具体字节。

无效地址常见原因：

  • 访问未分配内存。
  • 访问已经释放的堆内存。
  • 对只读内存执行写操作。
  • 用户态访问内核态内存或权限不足。
  • 页表项无效或物理页不可用。

后果通常是缺页异常、段错误或进程终止。

2.6 软件加载

操作系统创建进程通常包括：

  1. 创建虚拟地址空间。
  2. 根据可执行文件头建立虚拟地址与文件内容的映射。
  3. 初始化代码段、数据段、BSS、堆、栈。
  4. 加载动态链接器与共享库。
  5. 设置入口点，开始执行。

虚拟地址空间看似有限，但操作系统通过按需分页、缺页中断、copy-on-write、多级页表实现高效利用。

2.7 可执行文件、链接与重定位

共享代码的原因：

  • 多个程序可能使用同一套库函数。
  • 操作系统功能通常以共享库形式提供。
  • 共享库节省内存并提高维护效率。

静态链接：把库代码复制进最终可执行文件，程序独立性强，但体积大、更新困难。

动态链接：程序运行时加载共享库，多进程可共享同一代码页，节省内存，便于更新，但引入重定位与加载地址问题。

常见格式：

  • ELF：Linux 常见 Executable and Linkable Format。
  • PE：Windows 常见 Portable Executable。

ELF 有链接视图和执行视图：

  • 链接视图重视 section，如符号表、字符串表、重定位表。
  • 执行视图重视 segment，如程序头表描述如何加载到内存。

重定位的意义：目标文件编译时不知道外部符号最终地址，链接或加载时需要把符号引用修正到真实地址。

2.8 Rowhammer 与内存风水

Rowhammer 是硬件层面的内存扰动攻击。反复访问 DRAM 某一行可能导致相邻行电荷泄露，从而发生比特翻转。若翻转发生在页表、权限位等敏感位置，可能导致权限提升或数据篡改。

5352

[!note] 图意理解
这张 PPT 图展示 DRAM 的行、列和单元电容结构。Rowhammer 的“hammer”不是软件循环本身有魔法，而是高频访问某些行会影响相邻行电荷保持，最终可能把相邻行中的 bit 翻转。

防护思路：

  • 使用 ECC 内存检测/纠正错误。
  • 在内存控制器中限制高频访问模式。
  • 增加刷新。
  • 通过内存布局调整、隔离敏感区域，即“内存风水”，降低攻击者把目标对象摆放到相邻物理行的概率。

3. 栈溢出

3.1 栈的用途

栈保存函数调用过程中的短生命周期信息：

  • 函数参数。
  • 局部变量，包括局部数组。
  • 返回地址。
  • 保存的寄存器。
  • 上一栈帧的基址。

x86 32 位中，栈通常从高地址向低地址增长。后入栈的数据地址更低。每个数据单元常以 4 字节为基本粒度。

3.2 常用寄存器

ESP：栈顶指针。执行 push 时，ESP 减小，再写入数据；执行 pop 时，读取栈顶数据，再增大 ESP。

EBP：帧基指针。用于稳定定位函数参数和局部变量。通常参数位于 EBP 高地址侧，局部变量位于 EBP 低地址侧。

EIP：指令指针，保存下一条将要执行的指令地址。

EBX/ESI/EDI：常见调用者保存或被调用者保存相关寄存器，函数调用前后需要遵守调用约定，避免破坏调用者状态。

3.3 栈帧与函数调用

函数调用的核心是建立一个结构化栈空间，即栈帧。典型过程：

  1. 调用者准备参数。
  2. call 指令把返回地址压栈，并跳转到被调用函数。
  3. 被调用函数保存旧 EBP，把 ESP 赋给 EBP。
  4. ESP 下移，为局部变量分配空间。
  5. 函数执行。
  6. 恢复 ESP/EBP。
  7. ret 从栈顶弹出返回地址到 EIP，控制流回到调用者。

栈帧中最敏感的控制数据是返回地址。一旦返回地址被攻击者覆盖，ret 就可能跳到攻击者指定位置。

答案要点：ret 不会判断返回地址是否真来自合法调用点，它只按当前栈顶内容更新 EIP。如果栈溢出覆盖了返回地址，函数返回时 CPU 就会跳到攻击者写入的地址。

3.4 栈溢出的定义与原因

缓冲区是用于存放数据的一段连续内存。栈溢出是指向栈上的缓冲区写入超过其容量的数据，导致相邻栈数据被覆盖。

常见原因：

  • 使用 gets、不安全 strcpy、sprintf 等不检查长度的函数。
  • 程序员只考虑合法输入，未检查边界。
  • C/C++ 缺少自动边界检查。
  • 二进制底层细节复杂，局部变量、保存寄存器和返回地址相邻。

3.5 栈溢出的后果

轻则程序崩溃，重则控制流劫持。攻击者可能：

  • 覆盖局部变量，改变程序逻辑。
  • 覆盖保存的 EBP，影响栈展开。
  • 覆盖返回地址，使 EIP 跳到指定地址。
  • 传统代码注入中，把 shellcode 写入栈，再把返回地址指向 shellcode。

3.6 栈溢出方向

在 x86 中，栈向低地址增长，但数组写入通常从低地址向高地址连续写。若局部缓冲区位于返回地址下方，超长输入会“向高地址”越过缓冲区边界，覆盖保存的 EBP 和返回地址。

这里容易混淆：栈增长方向是高地址到低地址；缓冲区连续写入溢出方向取决于缓冲区地址与相邻对象排列，典型栈溢出会覆盖更高地址处的控制数据。

3.7 栈溢出防护

DEP/NX/W XOR X

DEP，即数据执行保护。核心思想是给内存页增加权限属性，使页面要么可写、要么可执行，避免 CPU 从数据区取指执行。硬件上常对应 NX bit。

优点：阻止传统“把 shellcode 放在栈/堆中执行”的攻击。

局限：不能阻止溢出发生，也不能发现溢出；如果攻击者不执行数据区，而是复用已有代码，DEP 不能直接防住。

Stack Canary

金丝雀是在局部缓冲区与返回地址之间放置检查值。函数返回前检查该值是否被破坏。若异常，说明可能发生栈溢出并终止程序。

8477

优点：能检测典型连续覆盖返回地址的溢出。

局限：有运行时开销；对未重新编译的遗产代码无效；若 canary 泄露或攻击不经过 canary，仍可能绕过。

Shadow Stack

影子栈是额外维护一份返回地址副本。call 发生时同时把返回地址写入影子栈；ret 发生前比较普通栈返回地址与影子栈副本。

8741

优点：专门保护返回地址完整性。

局限：运行开销和兼容性成本较高；对旧代码、特殊调用约定、手写汇编支持困难。

分离控制栈与数据栈

把控制流数据和普通数据放入不同栈空间。即便数据缓冲区溢出，也不容易覆盖返回地址。

8951

局限：需要操作系统、编译器、ABI 支持；对遗产代码和纯汇编函数兼容性差。

4. 堆、堆溢出与 ptmalloc

4.1 堆与栈的区别

栈：

  • CPU 和调用约定直接支持。
  • 连续、局部性好、访问快。
  • 自动分配释放。
  • 保存数据和控制流信息。
  • 溢出常破坏返回地址。

堆：

  • 由操作系统库函数和分配器管理。
  • 用于动态分配，生命周期由程序员控制。
  • 可能碎片化，访问局部性较弱。
  • 主要保存数据和分配器元数据。
  • 溢出常破坏相邻 chunk 或堆管理链表。

4.2 堆的创建与维护

常见接口：

  • malloc(size)：申请动态内存。
  • free(ptr)：释放动态内存。
  • brk/sbrk：调整进程堆顶位置。
  • mmap：直接映射匿名内存区域，常用于较大内存分配，地址分布可更离散。

常见分配器：

  • dlmalloc：通用分配器，嵌入式系统可见。
  • ptmalloc/ptmalloc2：glibc 常用。
  • jemalloc：FreeBSD、Firefox 等高并发场景。
  • tcmalloc：Google 等场景。

4.3 chunk 与元数据

分配器管理内存的基本单位是 chunk。一个 chunk 通常包含：

  • prev_size：前一个 chunk 大小，当前一个 chunk 空闲时有意义。
  • size：当前 chunk 大小，低位常夹带标志位。
  • P/PREV_INUSE：表示前一个 chunk 是否正在使用。
  • 用户数据区。
  • 空闲 chunk 还会把用户数据区的一部分复用为链表指针，如 fd、bk。

malloc 返回给用户的指针通常指向用户数据区，而不是 chunk 头部。free(ptr) 会根据用户指针回退找到 chunk 元数据。

这张图展示“用户指针并不指向 chunk 起始处”。粉色元数据在前，蓝色用户数据在后；分配器通过元数据记录大小、前后 chunk 状态和链表关系。堆溢出之所以危险，是因为用户数据区一旦写过界，就可能覆盖下一个 chunk 的元数据，而元数据会被 free/malloc 当作可信结构使用。

[!example] 随堂例题：malloc 返回的指针为什么不能直接 free(ptr + 1)？
答案要点：free 需要根据用户指针回退定位 chunk 头部。如果传入的不是原始 malloc 返回值，分配器会在错误位置解释元数据，轻则报错崩溃，重则破坏堆结构。这也说明用户指针和 chunk 元数据之间存在严格约定。

4.4 arena 与 bin

arena 是分配器从操作系统获得并管理的内存池。ptmalloc 中常见：

  • main arena：主线程使用，位于传统 heap 区。
  • thread arena：多线程场景中为线程分配，常通过 mmap 获取。

arena 维护多个结构：

  • fastbinsY：小块快速链表。
  • bins：small bin、large bin、unsorted bin 等。
  • top：位于堆顶、可继续切分的 top chunk。
  • last_remainder：上次切分剩余块。

bin 的本质是空闲 chunk 的链表或数组。堆空间的维护本质上就是维护这些 bin 链表。

4.5 分配、释放与合并

分配流程简化理解：

  1. malloc 根据请求大小对齐并加上元数据开销。
  2. 先在对应大小的空闲链表中查找可用 chunk。
  3. 若找到，unlink 或弹出该 chunk 返回给用户。
  4. 若找不到，从 top chunk 切分。
  5. 若 top chunk 不够，调用 sbrk 或 mmap 向操作系统申请更多内存。

释放流程简化理解：

  1. free 根据用户指针找到 chunk。
  2. 修改 chunk 状态为空闲。
  3. 检查前后相邻 chunk 是否空闲。
  4. 空闲则尝试合并，减少碎片。
  5. 把合并后的 chunk 放入合适 bin。
  6. 若与 top chunk 合并且足够大，可能把内存归还给操作系统。

[!note] 图意理解
这张图对应 free 的“合并”动画：释放中间 chunk 后，分配器检查前后相邻 chunk 的状态。如果相邻 chunk 也空闲，就尝试合并；若最终与 top chunk 连在一起，并且空间超过阈值，就可能移动 break，把一部分堆空间还给操作系统。考试中要把“释放”理解为“更新分配器数据结构”，不是简单把内存清零。

4.6 fastbin

fastbin 用于频繁申请/释放的小尺寸 chunk。特点：

  • 单向链表。
  • LIFO，后释放的先被重新分配。
  • 通常不立即与相邻 chunk 合并。
  • 检查相对宽松，主要检查大小等基本合法性。

fastbin 提高性能，但历史上也提供了攻击面。攻击者若能篡改空闲 chunk 的 fd 指针，可能诱导后续 malloc 返回伪造地址附近的 chunk。

4.7 堆溢出

堆溢出是指向堆上缓冲区写入超过其大小的数据，破坏相邻堆块的用户数据或元数据。

与栈溢出不同：

  • 堆通常向高地址增长。
  • 堆溢出不一定直接覆盖返回地址。
  • 主要破坏 chunk header、bin 链表指针、对象函数指针、虚表指针、长度字段等。

危害：

  • 程序崩溃。
  • 任意地址读写。
  • 劫持函数指针、GOT、hook 或对象虚表。
  • 结合控制流劫持实现代码执行。

4.8 fastbin 攻击原理

核心思想：利用堆溢出或 double free 篡改 fastbin 单链表，使后续 malloc 返回攻击者希望控制的地址。

概念流程：

  1. 准备同尺寸小 chunk，并释放到 fastbin。
  2. 利用漏洞篡改空闲 chunk 的 fd。
  3. 构造满足分配器基本检查的 fake chunk。
  4. 连续申请同尺寸内存，让 malloc 沿被篡改链表返回 fake chunk。
  5. 攻击者获得对目标地址附近内容的写能力。

4.9 unlink 攻击原理

unlink 是从双向空闲链表中移除 chunk 的操作。双向链表中：

  • fd 指向下一个空闲 chunk。
  • bk 指向上一个空闲 chunk。

当 free 一个 chunk 时，glibc 会检查前后相邻 chunk 是否空闲，若空闲则合并。合并时需要把被合并的空闲 chunk 从 bin 中 unlink。

历史 unlink 攻击利用点：如果攻击者能伪造 fd 和 bk，unlink 的指针更新可能变成任意地址写。

13430

[!note] 图意理解
第一张图是 unlink 宏的核心：FD = P->fd、BK = P->bk，随后执行 FD->bk = BK 和 BK->fd = FD。第二张图说明攻击者伪造 fd/bk 后，这两次链表修复写操作可能落到攻击者选择的目标地址。现代 glibc 的双链表一致性检查就是为阻止这种伪造。

向后合并：当前 chunk 释放时，如果前一个 chunk 空闲，通过当前 chunk 的 PREV_INUSE 位和 prev_size 找到前一个 chunk，并将其从链表中移除后合并。

向前合并：如果后一个 chunk 空闲，将后一个 chunk 从链表中移除并合并到当前 chunk。

典型伪造思路：

  1. 通过堆溢出覆盖相邻 chunk 的头部。
  2. 清除 PREV_INUSE 标志，使分配器误以为前一个 chunk 空闲。
  3. 伪造 prev_size、fd、bk。
  4. 触发 free 合并和 unlink。
  5. 借由链表指针写入影响目标地址。

4.10 unlink 防护

现代 glibc 已增加多种检查：

  • Double free 检测：不允许释放已经处于 free 状态的 chunk。
  • next size 合法性检测：检查相邻 chunk size 是否在合理范围内。
  • 双链表一致性检测：检查 P->fd->bk == P 且 P->bk->fd == P。

因此考试中应说明：堆攻击往往依赖具体分配器版本；防御比栈溢出更依赖系统库升级。

5. 整数溢出漏洞

5.1 整数表示

常见类型：

  • short：16 bit。
  • int：32 bit。
  • long：课程笔记按 64 bit 说明，实际依平台 ABI 而定。

无符号整数范围：0 到 2^n - 1。

有符号整数范围：-2^(n-1) 到 2^(n-1)-1。

带符号整数通常用补码表示。正数不变，负数按位取反再加 1。补码的意义是统一加法和减法，符号位与数值域可以一起参与运算。

5.2 溢出规则

C 语言中：

  • unsigned 溢出按模 2^n 运算，是定义明确的回绕。
  • signed 溢出是 undefined behavior，编译器可基于“不发生溢出”的假设优化代码。

CPU 有 FLAG 寄存器记录进位、溢出等状态，但高级语言程序常忽略检查，导致边界错误进入内存分配、长度计算、循环判断等敏感位置。

14628

[!note] 图意理解
老师在整数溢出部分放 CPU FLAG 图，是为了说明硬件层面其实能产生进位/溢出等状态信息；问题在于 C/C++ 程序和编译器优化并不总会把这些状态当作安全检查使用。因此安全代码必须显式检查长度和范围。

5.3 整数溢出的安全后果

整数溢出本身不一定直接造成控制流劫持，但常作为前置漏洞导致：

  • 分配长度变小：count * size 溢出后申请了过小缓冲区，后续写入按原始大长度执行，形成缓冲区溢出。
  • 边界检查绕过：负数转换为无符号大数，或大数回绕为小数。
  • 数组索引错误：索引越界读写。
  • 权限判断错误：金额、计数、剩余长度等逻辑被绕过。

[!note] 图意理解
这张 PPT 图对应典型模式：先从报文读取一个整数 nresp，再用 nresp * sizeof(...) 分配内存，最后按 nresp 循环写入。如果乘法溢出导致申请空间变小，循环仍按大 nresp 写入，就把整数溢出转化成堆溢出。

5.4 防护

  • 在可能溢出的位置之前检查，不要在计算之后才检查。
  • 对乘法、加法、长度转换使用安全函数或编译器内建溢出检测。
  • 避免 signed/unsigned 混用。
  • 对外部输入进行范围限制。
  • 使用更大类型时仍要检查边界，因为类型扩大不是根本防护。
  • 编译器和静态分析工具可检测部分 integer-overflow-to-buffer-overflow 问题。

7.2 SQL 注入定义

SQL 注入是指攻击者把输入数据构造成 SQL 语法的一部分，使服务端原本预设的 SQL 语句结构被改变，从而绕过条件判断、权限控制或执行非预期数据库操作。

本质：把“数据”误解析成“代码/命令”。这与格式化字符串漏洞相似，都是解释器边界混淆。

SQL 注入常用基础符号：

  • ;：语句结束。
  • '：字符串闭合。
  • # 或 --：注释后续内容。
  • and 1=1 / and 1=2：用于判断条件是否可控。

7.3 SQL 注入流程

笔记中的 7 步流程：

  1. 寻找可能存在 SQL 注入漏洞的链接。
  2. 测试该网站是否有 SQL 注入漏洞。
  3. 猜管理员账号表。
  4. 猜管理员表中的字段。
  5. 猜测用户名和密码长度。
  6. 猜测用户名。
  7. 猜测密码。

复习时不要只背步骤，要理解每一步目的：从“入口可控”到“语句结构可控”，再到“数据库结构推断”，最后到“敏感数据获取”。

  4. 数据库按新的语法树执行。
  5. 造成越权登录、数据泄露、篡改或删除。

7.7 SQL 注入防御

核心防御是让 SQL 结构和用户数据分离。

有效措施：

  • 使用预编译语句/参数化查询。SQL 引擎先解析模板语法树，用户输入只作为字面值参数，不参与改变语法结构。
  • 严格输入验证：类型、长度、格式、白名单。
  • 对特殊字符进行正确转义，但不要把转义当作唯一防御。
  • 最小权限：Web 应用数据库账号只授予必要权限。
  • 关闭详细错误回显，避免泄露表名、字段名、SQL 片段。
  • 使用 ORM 或安全数据库接口，但仍需理解其边界。

关键词过滤不是可靠防御。过滤标签、关键字或特殊符号容易被编码、大小写、拼接、注释、替代语法绕过。

7.8 数组越界访问

数组越界访问是程序访问了数组合法范围之外的内存。可能造成：

  • 越界读：信息泄露。
  • 越界写：破坏相邻对象或控制数据。
  • 崩溃。

典型例子：OpenSSL Heartbleed。成因是处理 heartbeat response 时没有检查包长度合法性，直接按攻击者声明的长度读取并返回内存，导致越界读和敏感信息泄露。

8. Double Free 与 Use-After-Free

8.1 指针悬空

堆块释放后，原本指向它的指针不会自动失效。如果程序继续保存并使用这个指针，它就成为悬空指针。

悬空指针危险在于：该地址可能已经被分配给新对象，旧指针和新指针就会引用同一块内存，但程序逻辑认为它们属于不同对象。

8.2 Double Free

Double free 是对同一块动态内存释放两次。C 标准中对这种行为的规定是 undefined behavior。

这组图的核心是“同一 chunk 被释放两次后，分配器的空闲链表状态被污染”。第一次 free(P) 后，P 进入 bin；第二次 free(P) 后，链表里逻辑上出现同一个 chunk 的重复引用。随后第一次 malloc 把 P 返回给用户，但 bin 中仍可能保留指向 P 的关系；用户写入的数据会覆盖空闲 chunk 原本用于 fd/bk 的位置。下一次 malloc 再按空闲链表解释这些位置时，就会把用户数据当成地址和值使用，造成分配异常或任意写条件。

[!example] 随堂例题：为什么释放后要把指针置为 NULL？
答案要点：释放后原指针仍保存旧地址，成为悬空指针。置为 NULL 可以让重复释放变成 free(NULL) 这种无害操作，也能减少 UAF 中继续通过旧指针访问已释放内存的风险。但置空只保护当前变量，若还有其他别名指针，仍需所有权管理。

爆发点：

  • 堆块合并。
  • unlink。
  • bin 链表维护。

典型后果：

  • 空闲链表被破坏。
  • 同一 chunk 被多次放入 bin。
  • 后续 malloc 可能把同一地址分配给两个对象。
  • 攻击者可借机修改链表指针或关键数据。

防护：

  • 释放后立即把指针置为 NULL。
  • 明确对象所有权，避免多处释放同一资源。
  • 使用 RAII、智能指针或安全内存管理。
  • 启用 AddressSanitizer、堆检查器、现代分配器 double free 检测。

8.3 Use-After-Free

释放重引用漏洞，即 use-after-free，流程：

  1. 申请空间，得到指针 p1。
  2. 释放 p1 指向的空间，但不把 p1 置空。
  3. 再次申请空间 p2，分配器可能复用刚释放的地址。
  4. 攻击者通过 p2 布置数据。
  5. 程序继续使用悬空指针 p1，把新数据当作旧对象解释。

Double free 可以看作释放重引用问题的一个特例。

UAF 常见危害：

  • 类型混淆。
  • 虚函数表劫持。
  • 函数指针覆盖。
  • 权限对象被篡改。

防护：

  • 明确生命周期与所有权。
  • 释放后置空。
  • 避免裸指针长期跨模块保存。
  • 使用引用计数、智能指针、生命周期分析。
  • 运行时使用 ASan、UBSan、GWP-ASan 等检测工具。

9. XSS 与 CSRF

9.1 XSS 定义

XSS，即跨站脚本。攻击者构造畸形输入，使其以访问者身份在目标站点上下文中执行 HTML/JavaScript 代码。

本质：HTML/JavaScript 注入。服务器或客户端把用户输入当成页面结构或脚本执行，而不是普通文本显示。

9.2 XSS 分类

存储型 XSS：恶意脚本被存入正常服务器，如评论、留言、个人资料。其他用户访问页面时触发。危害大，因为不需要诱导每次携带恶意 URL。

反射型 XSS：恶意代码不存储在服务器，而是通过 URL 或请求参数提交，服务器把输入反射到响应页面，用户点击链接时触发。非持久型。

DOM 型 XSS：漏洞发生在客户端 JavaScript 对 DOM 的解析和写入过程中，不一定需要服务器参与。可视为特殊反射型，但核心在浏览器端脚本。

9.3 DOM

DOM，文档对象模型，是浏览器把网页组织成树形对象结构的标准模型。JavaScript 可以读取和修改 DOM 节点。DOM 型 XSS 常来自 innerHTML、document.write、URL hash、location、postMessage 等不安全使用。

9.4 XSS 发生条件

  1. 存在用户可控输入。
  2. 输入被输出到页面或进入 DOM。
  3. 输出位置缺少正确编码或过滤。
  4. 浏览器把输入解释为标签、属性、事件或脚本。

不同上下文需要不同防护：

  • HTML 文本内容：HTML 实体编码。
  • HTML 属性：属性编码并加引号。
  • JavaScript 字符串：JS 字符串编码。
  • URL：URL 编码与协议白名单。
  • CSS：谨慎处理，尽量不拼接用户输入。

9.5 XSS 防御

  • 输出编码优先于黑名单过滤。
  • 按上下文编码，而不是统一替换几个字符。
  • 对富文本使用成熟 HTML sanitizer。
  • 设置 HttpOnly Cookie，降低脚本窃取 Cookie 风险。
  • 设置 SameSite、Secure、CSP。
  • 避免危险 DOM API 或使用安全封装。
  • 输入校验用于减少非法数据，但不能替代输出编码。

过滤机制容易被绕过，例如构造不存在标签、关键字拆分、运行时拼接、编码变形、大小写混合、特殊符号变体。

9.6 CSRF 定义

CSRF，即跨站请求伪造。攻击者诱导已登录用户访问恶意页面，恶意页面借助用户浏览器中已有的登录态，向目标网站发送非用户本意的请求。

核心条件：

  1. 用户已登录目标站点。
  2. 浏览器自动携带 Cookie 或会话标识。
  3. 目标站点只凭 Cookie 判断身份。
  4. 敏感操作缺少额外确认或 CSRF token。

9.7 CSRF 流程

  1. 用户正常登录网站。
  2. 网站创建 session，浏览器保存 Cookie。
  3. 用户保持登录状态。
  4. 用户访问攻击者设置的页面。
  5. 恶意页面自动发起请求到目标站点。
  6. 浏览器自动带上目标站点 Cookie。
  7. 目标站点误以为是用户真实操作，执行配置修改、发帖、取消会员等动作。

[!note] 图意理解

9.8 CSRF 防御

  • CSRF Token：在表单或请求头中加入攻击者无法预测的随机值。
  • SameSite Cookie：限制跨站请求携带 Cookie。
  • 对敏感操作使用 POST 并校验 Origin/Referer。
  • 二次确认、验证码、重新输入密码用于高风险操作。
  • 不要用 GET 执行有副作用的操作。

笔记提到“在 URL 请求中引入伪随机数”和“类似 SQL 请求的随机化”，本质就是让攻击者无法伪造完整合法请求。

10. 代码注入、Ret2libc 与 ROP

10.1 经典代码注入

经典代码注入思路：

  1. 利用逻辑异常或缓冲区溢出，在程序数据区混入 shellcode。
  2. 覆盖返回地址或函数指针，劫持控制流。
  3. 使 EIP 跳到数据区。
  4. CPU 把攻击者写入的数据当作指令执行。

弱点：早期 CPU/系统不能区分某块内存是代码还是数据。

10.2 DEP 防御与局限

DEP/W XOR X/NX 让数据页不可执行，从而阻止“跳到栈/堆 shellcode”的传统攻击。

局限：如果攻击者复用程序已有代码，而不是执行数据页，DEP 不足以阻止。例如 ret2libc 和 ROP。

10.3 Return-to-libc

Return-to-libc 是代码重用攻击的早期形式。攻击者通过缓冲区溢出把返回地址改为系统库函数地址，并在栈上布置该函数参数。

特点：

  • 不注入新代码。
  • 直接调用 libc 等共享库中的已有函数。
  • 能绕过不可执行栈。
  • 攻击能力受已有函数粒度限制，但可通过调用链增强。

10.4 x86 CISC 与代码重解释

x86 指令长度可变，一个字节的意义取决于上下文。控制流如果跳入一段合法代码的中间位置，CPU 可能从新的边界重新解释字节流，产生原程序员未预期的短指令片段。

这为 ROP 寻找 gadget 提供了基础。

10.5 ROP 返回导向编程

ROP，即 Return-Oriented Programming。攻击者不注入代码，而是在程序和共享库已有代码中寻找以 ret 结尾的短指令片段，即 gadget，再把这些 gadget 地址按顺序布置在栈上。

ret 的效果：

  1. 从当前栈顶读取一个地址。
  2. 把该地址写入指令指针。
  3. 栈指针移动到下一个位置。

因此，如果栈上连续摆放多个 gadget 地址，每次 ret 都会跳到下一个 gadget，形成攻击者拼接的“程序”。

[!example] 随堂例题：ROP 为什么能绕过 DEP？
答案要点：DEP 只阻止数据页执行。ROP 执行的是程序或共享库中已有的合法代码片段，攻击者只是在栈上布置这些片段的地址，因此不需要从栈或堆执行 shellcode。

10.6 ROP 与图灵完全

若 gadget 集合能实现：

  • 加载/存储。
  • 算术与逻辑。
  • 控制流。

则可模拟通用计算，即接近图灵完全。ROP 的强大之处在于用合法代码片段拼出任意恶意行为。

10.7 ROP 难点与检测困难

难点：

  • 需要搜索整个代码空间找到合适 gadget。
  • 需要知道 gadget 地址。
  • 需要控制栈内容。
  • 需要绕过 ASLR、canary、CFI 等防护。

检测困难：

  • 执行的代码本身是程序中已有合法代码。
  • 单个 gadget 短小，看起来不像完整恶意代码。
  • 攻击逻辑由栈上地址序列表达。

11. ASLR 地址空间随机化

11.1 ASLR 基本思想

ASLR 通过随机化进程内存布局增强多样性。同一程序在不同机器或同一机器不同运行中，代码、库、堆、栈等位置不同。

ROP 和 ret2libc 依赖 gadget 或库函数地址已知且稳定。ASLR 让攻击者原本计算的地址失效，跳转到旧地址会导致崩溃。

11.2 粗粒度 ASLR

粗粒度 ASLR 通常随机化区域基址：

  • 可执行区域：代码段、初始化数据、未初始化数据。
  • 映射区：堆、动态库、共享内存。
  • 栈区。

在 32 位系统中，随机化空间受限。例如页对齐会固定低 12 位，高位还要考虑全局页表和地址空间布局，因此有效随机位数有限。

11.3 粗粒度 ASLR 局限

主要局限：

  • 32 位随机化强度不足。若只有 16 位随机性，平均约 2^15 = 32768 次尝试可命中。
  • 只随机化基址，不改变模块内部相对偏移。
  • 一旦泄露一个代码指针，可推算同模块其他 gadget 或函数地址。
  • 长时间运行的服务进程布局不变，攻击者可多次尝试。

笔记中提到实验：对部署 ASLR 的 Apache Http Server 进行暴力尝试，平均耗时约 216 秒即可成功，说明低熵 ASLR 防护有限。

11.4 细粒度 ASLR

细粒度 ASLR 从“区段间随机化”发展到“区段内随机化”，尝试改变代码文本内部结构。

实施方式：

  • 程序加载时自我随机化。
  • 通过虚拟机动态随机化。
  • 操作系统级随机化。

目标是让攻击者即便知道模块基址，也难以确定具体 gadget 地址。

11.5 ASLR 无效化

ASLR 假设攻击者无法完整披露内存空间，或最多只能获得有限代码指针。

绕过思路：

  • 信息泄露：泄露库函数、返回地址、对象指针。
  • 暴力猜测：随机空间小且服务可反复尝试时可行。
  • Page harvest：利用一个已有代码指针，按 4KB 页大小遍历，逐步暴露进程代码和 API 资源。
  • JIT-ROP：运行时动态收集可用 gadget。

ASLR 关键局限：程序运行时通常不持续改变内存空间结构，一旦布局被泄露，随机化收益大幅下降。

12. 模糊测试 Fuzzing

12.1 起源与定义

Baron Miller 的早期思想来自通信线路噪声导致程序崩溃的观察。他创建随机字符生成程序和交互程序，向 Unix 工具输入随机字符串，观察是否崩溃，再分析崩溃原因并归类公共错误。

Fuzzing 是一种发现安全漏洞的自动化测试方法：把随机、畸形、超出预期的数据输入程序，观察程序是否能容忍杂乱输入。

与功能测试区别：

  • 功能测试关心是否按预期完成业务功能。
  • Fuzzing 关心程序在异常输入下是否崩溃、中断、破坏或暴露漏洞。

12.2 Fuzzing 本质

Fuzzing 的思想是用“暴力”自动化试探目标程序：

  1. 持续生成不同格式、长度、结构的数据。
  2. 输入目标程序。
  3. 监控崩溃、异常、超时、内存错误。
  4. 保存触发异常的测试用例。
  5. 分析根因和可利用性。

Fuzzing 能发现逻辑思维测试难以覆盖的问题，因为它不受程序员预设合法输入框架限制。

12.3 使用对象

攻击者：寻找未公开 0day 漏洞，用于攻击链。

安全专家/工业界：在攻击者之前发现并修复漏洞，提高软件质量。

12.4 Fuzzing 特征

  • 测试用例具有攻击性和畸形性。
  • 自动化程度高。
  • 暴力/蛮力。
  • 误报少，因为崩溃通常是真实问题。
  • 能快速找到真实漏洞。
  • 操作相对简单。
  • 不能证明程序没有漏洞。即使找到 100 个严重漏洞，也可能存在第 101 个。

12.5 常规步骤

  1. 识别测试目标。
  2. 识别用户输入。
  3. 生成 Fuzz 测试数据。
  4. 执行 Fuzz 测试数据。
  5. 监视异常。
  6. 保存测试用例和异常信息。
  7. 确定可利用性。

截图中的流程可概括为：产生或获取数据 -> 发送给应用程序 -> 判断运行失败或出现问题 -> 若无异常则继续生成数据 -> 若有异常则保存用例和异常信息。

12.6 简单缓冲区溢出 Fuzz 示例

对一个接收命令行参数的程序，不断输入不同长度字符串：

  1. 从短字符串开始。
  2. 逐步增加长度。
  3. 观察何时崩溃。
  4. 保存触发崩溃的输入。
  5. 调试确认是否覆盖返回地址或其他关键数据。

这类测试可发现长度检查缺失导致的缓冲区溢出。

12.8 Smart Fuzz

Smart Fuzz 是为提高有效性而出现的方法。

面向逻辑：

  • 测试目标是解析程序逻辑，而不是盲目破坏文件。
  • 明确测试深度和畸形数据粒度。
  • 尽量只改动特定位置，保持其他依赖关系合法，使数据能传递到深层解析器。

面向数据类型：

  • 识别字段类型后按类型生成畸形数据。
  • 算术型：极大值、极小值、边界值、不同编码形式。
  • 指针型：NULL、非法地址、边界地址。
  • 字符串型：超长字符串、缺少 0x00 终止符。
  • 特殊字符：#、@、引号、尖括号、斜杠、路径穿越符号等。

基于样本：

  • 先构造合法样本文件。
  • 每次只变异一小部分数据或逻辑。
  • 对复杂格式更容易实现。
  • 漏报风险：样本中没有覆盖的数据结构不会被测试。
  • 提高质量的方法是构造包含文字、图像、视频、声音、版权信息等尽可能多结构的样本。

12.12 XSS 盲打

常规 XSS 通过页面返回内容判断脚本是否执行。但反馈、工单等功能可能不把提交内容返回给提交者，只显示“感谢反馈”。此时可以使用 XSS 盲打。

盲打思路：

  1. 在盲打平台建立项目，生成回连脚本地址。
  2. 把脚本链接或触发代码提交到目标输入点。
  3. 当管理员后台审核内容时，如果脚本执行，会向盲打平台发送请求并带回信息。
  4. 平台收到回连说明攻击触发。

考试表述重点：盲打适用于提交后不回显但会被后台人员查看的场景，常见目标是反馈、留言、工单、日志查看后台。

13. 防护机制横向总结

13.1 内存漏洞防护

输入与边界：

  • 检查长度、索引、整数范围。
  • 禁用危险函数。
  • 使用安全容器和安全 API。

编译期：

  • 栈保护 canary。
  • PIE，为 ASLR 提供可随机化代码基址。
  • FORTIFY_SOURCE。
  • 静态分析。

运行期：

  • DEP/NX。
  • ASLR。
  • Shadow stack。
  • CFI。
  • 堆分配器一致性检查。
  • ASan 等检测工具。

工程层面：

  • 代码审计。
  • Fuzzing。
  • 单元测试和边界测试。
  • 最小权限与隔离。

13.2 Web 漏洞防护

SQL 注入：

  • 参数化查询。
  • 最小权限。
  • 输入白名单。
  • 错误信息收敛。

XSS：

  • 按上下文输出编码。
  • 富文本 sanitizer。
  • CSP。
  • HttpOnly/SameSite Cookie。

CSRF：

  • CSRF token。
  • SameSite Cookie。
  • Origin/Referer 校验。
  • 敏感操作二次确认。

13.3 防护机制共同局限

单点防护不够。DEP 可被 ROP 绕过；ASLR 可被信息泄露削弱；过滤可被编码和语法变形绕过；canary 可被泄露或非连续写绕过；Fuzzing 不能证明没有漏洞。

正确思路是多层防御：减少漏洞产生、限制漏洞触发、检测异常、降低利用稳定性、降低攻击后权限和影响。

14. 高频问答题答案骨架

14.1 简述进程内存空间结构

进程拥有独立虚拟地址空间。典型布局从低到高包括 code/text、data、BSS、heap、mmap/shared libraries、stack。Code 保存机器指令，通常只读共享；Data 保存已初始化全局/静态变量；BSS 保存未初始化全局/静态变量，加载时置零；Heap 用于动态分配，malloc/free 管理；Stack 用于函数调用，保存参数、局部变量、返回地址等。虚拟地址经 MMU 和页表映射到物理地址，并通过权限位提供隔离和保护。

14.2 简述栈溢出

栈溢出是向栈上缓冲区写入超过容量的数据，覆盖相邻栈内容。由于栈帧中保存局部变量、旧 EBP、返回地址等，溢出可能覆盖返回地址，使函数返回时跳转到攻击者控制地址。原因包括不安全字符串函数、缺少边界检查、C/C++ 不自动检查数组边界。后果包括崩溃、变量篡改、控制流劫持。防护包括 DEP、canary、shadow stack、分离控制/数据栈、ASLR 和安全编程。

14.3 简述堆溢出

堆溢出是对堆上动态分配缓冲区写入超长数据，破坏相邻 chunk 用户数据或元数据。堆由分配器维护，chunk 中包含 size、prev_size、标志位、空闲链表指针等。攻击者可通过破坏 fastbin/unlink 链表指针造成任意写或诱导 malloc 返回指定位置。防护依赖现代分配器检查、库升级、边界检查、ASan 和安全生命周期管理。

14.4 简述 double free

Double free 是同一块堆内存被释放两次。释放后指针不自动销毁，若再次 free 悬空指针，会触发 undefined behavior。其危险点在于破坏 bin 链表和堆块合并过程，可能导致同一 chunk 被重复分配或链表指针被攻击者控制。防护包括释放后置空、明确所有权、避免重复释放、使用智能指针和现代分配器检测。

14.5 简述 use-after-free

Use-after-free 是对象释放后仍通过悬空指针访问。若该内存被重新分配给新对象，旧指针会把新对象内容当作旧对象解释，造成类型混淆、虚表劫持、函数指针覆盖等。防护包括释放后置空、所有权管理、RAII、引用计数、生命周期分析和运行时检测。

14.6 简述格式化字符串漏洞

格式化字符串漏洞发生在程序把用户输入直接作为 printf 等函数的 format 参数。攻击者构造 %x 可读取栈数据，构造 %s 可把值当作指针读取内存，构造 %n 可向指定地址写入已输出字符数。后果包括信息泄露、任意读写和控制流劫持。防护是使用固定格式字符串，如 printf("%s", input)，并开启编译器检查。

14.7 简述 SQL 注入及防御

SQL 注入是用户输入被拼接进 SQL 后改变语句结构，使条件判断失效或执行非预期数据库操作。攻击流程包括寻找入口、测试注入、推断表名字段、获取敏感数据。数字型可用 and 1=1/and 1=2 判断，字符型需要闭合引号。防御核心是参数化查询，让 SQL 结构与用户数据分离；还应输入白名单、最小权限、错误信息收敛。

14.8 简述 XSS

XSS 是攻击者把 HTML/JavaScript 注入到网页中，使脚本在受害者浏览器和目标站点上下文执行。本质是 HTML 注入。类型包括存储型、反射型、DOM 型。防御包括按上下文输出编码、使用 sanitizer、CSP、HttpOnly/SameSite Cookie 和避免危险 DOM API。

14.9 简述 CSRF

CSRF 是攻击者利用用户已登录状态，诱导浏览器向目标站点发送非用户本意请求。浏览器自动携带 Cookie，目标站点若只凭 Cookie 判断身份，就会执行敏感操作。防御包括 CSRF token、SameSite Cookie、Origin/Referer 校验、敏感操作二次确认，以及禁止 GET 执行有副作用操作。

14.10 简述 ROP

ROP 是返回导向编程。DEP 使数据区不可执行后，攻击者不再注入代码，而是在已有代码中寻找以 ret 结尾的 gadget，并通过控制栈上的返回地址序列把 gadget 串联起来，实现任意计算或恶意行为。ROP 难检测，因为执行的是合法代码片段。防护包括 ASLR、CFI、shadow stack、代码随机化等。

14.11 简述 ASLR 及不足

ASLR 通过随机化代码、库、堆、栈等区域地址，使攻击者难以预测 gadget 和函数地址。粗粒度 ASLR 只随机化区域基址，模块内部相对偏移不变；32 位系统随机位数有限，可被暴力猜测；信息泄露一个代码指针后可推算其他地址。细粒度 ASLR 进一步随机化区段内部和代码内容，但也有性能、兼容性和运行时泄露问题。

14.12 简述 Fuzzing

Fuzzing 是向程序输入随机或畸形数据，观察程序是否崩溃或异常，从而发现漏洞的自动化测试方法。步骤包括识别目标、识别输入、生成测试数据、执行、监控异常、保存用例、分析可利用性。类型包括文件 Fuzz、协议 Fuzz、Web Fuzz、XSS Fuzz。优点是自动化、误报少、能发现真实漏洞；缺点是不能证明没有漏洞，覆盖依赖样本和生成策略。

15.1 SQL 注入综合题

  2. 漏洞点：用户输入未按输出上下文编码。
  3. 类型判断：存储型、反射型、DOM 型。

15.3 Fuzzing 综合题

可按以下结构答：

  1. 定义：自动生成畸形输入测试目标程序异常处理能力。
  2. 目标：发现崩溃、内存错误、拒绝服务、解析漏洞。
  3. 流程：目标 -> 输入 -> 生成 -> 执行 -> 监控 -> 保存 -> 分析。
  4. 类型：文件、协议、Web、XSS。
  5. 方法：Blind Fuzz、Smart Fuzz、面向逻辑、面向数据类型、基于样本。
  6. 优缺点：自动化、误报少、能找真实漏洞；不能证明无漏洞，覆盖依赖策略。
  7. 例子：文件解析器变异长度字段；Web 参数随机字符串确认注入点；协议报文字段变异并监控服务端异常。

16. 易混点对照

栈增长方向 vs 栈溢出覆盖方向：栈通常向低地址增长，但缓冲区连续写入可能向高地址覆盖返回地址。

堆溢出 vs double free：堆溢出是越界写破坏相邻内存；double free 是同一内存释放两次破坏分配器状态。

UAF vs double free：UAF 是释放后继续使用；double free 是释放后再次释放。double free 可视为释放重引用问题的特例。

DEP vs ASLR：DEP 阻止数据区执行；ASLR 随机化地址。DEP 防 shellcode，ASLR 防地址预测。

Ret2libc vs ROP：Ret2libc 调用已有库函数；ROP 拼接多个短 gadget，表达能力更强。

SQL 注入 vs XSS：SQL 注入把输入解释为数据库命令；XSS 把输入解释为 HTML/JavaScript。

XSS vs CSRF：XSS 是脚本在目标站点上下文执行；CSRF 是伪造用户已登录请求，不一定执行脚本。

过滤 vs 编码：过滤试图删除危险内容，容易绕过；编码把内容固定解释为数据，是 XSS 防御核心。

Fuzzing vs 功能测试：功能测试验证正常功能；Fuzzing 验证异常输入下是否崩溃或出错。

19. 答案与解析

19.1 选择与判断答案

  1. 已初始化全局变量通常在 Data；未初始化静态变量通常在 BSS；局部数组在栈；malloc 返回指向的用户数据在堆；字符串常量通常在只读常量区或 Text 相关只读区域。解析：变量本身和指向对象要分开判断。

  2. 错。p 是局部指针变量时通常在栈上，p 指向的 32 字节用户数据在堆上。解析：这是内存布局题最常见陷阱。

  3. Intel 通常目的操作数在左、源操作数在右；AT&T 通常源在左、目的在右。AT&T 寄存器加 %、立即数加 $，间接寻址用 ()，并用 b/w/l 等后缀表示宽度；Intel 常用 [] 和 BYTE/WORD/DWORD。解析：看汇编前必须先确认语法格式。

  4. 错。DEP/NX 阻止数据页执行，不能阻止溢出发生，也不能发现溢出。解析：ROP/ret2libc 能复用已有代码绕过 DEP。

  5. 错。ASLR 提高地址预测难度，但会受随机熵不足、信息泄露、长时间运行服务和模块内相对偏移不变等问题影响。解析：ASLR 是概率防御，不是根因修复。

  6. 对。SQL 注入把输入当数据库命令结构，XSS 把输入当 HTML/JavaScript，格式化字符串把输入当 format，底层共同点都是解释边界混淆。

  7. 对。CSRF 借助浏览器自动携带 Cookie 的机制伪造用户请求，所以 token、SameSite、Origin/Referer 校验都围绕“请求是否真由用户页面发起”展开。

  8. 错。Fuzzing 只能证明“这些测试用例没有触发已监控异常”，不能证明不存在漏洞。解析：覆盖率和生成策略决定 Fuzzing 能看到多深。

19.2 简答题答案

  1. 典型布局包括 Code/Text、Data、BSS、Heap、mmap/shared libraries、Stack。Code 存机器码，Data 存已初始化全局/静态变量，BSS 存未初始化全局/静态变量，Heap 动态分配，Stack 保存函数调用信息。理解布局后，才能解释为什么栈溢出会覆盖返回地址、堆溢出会破坏 chunk 元数据。

  2. call 把返回地址压栈并跳转；被调用函数保存旧 EBP，把 ESP 赋给 EBP 建立栈帧；通过移动 ESP 为局部变量分配空间；返回时恢复 ESP/EBP；ret 从栈顶弹出返回地址到 EIP。解析：返回地址是栈溢出的关键控制数据。

  3. 栈溢出是向栈上缓冲区写入超过容量的数据，覆盖相邻栈内容，可能覆盖旧 EBP、返回地址或局部变量。后果包括崩溃、变量篡改、控制流劫持。防护包括安全 API 和边界检查、DEP/NX、canary、shadow stack、ASLR、分离控制/数据栈。

  4. chunk 由元数据和用户数据组成，malloc 返回用户数据区指针，元数据通常位于用户数据前。若用户数据写过界，会覆盖相邻 chunk 的 prev_size/size/P/fd/bk 等信息；后续 free/malloc 会把这些被污染的数据当作分配器结构解释。

  5. arena 是分配器管理的内存池；fastbin 是小 chunk 快速单链表；bins 是 small/large/unsorted 等空闲链表入口；top chunk 是堆顶可继续切分的剩余空间。解析：堆管理本质是维护这些链表和 top chunk。

  6. fastbin 攻击利用 fastbin 单链表和后进先出分配特点，通过堆溢出或 double free 篡改空闲 chunk 的 fd 指针，使后续 malloc 沿伪造链表返回攻击者指定位置附近的内存。

  7. unlink 从双向空闲链表移除 chunk 时会更新 fd/bk。历史实现缺少一致性检查时，伪造 fd/bk 可把链表更新变成任意地址写。现代 glibc 会做 double free、next size 合法性、P->fd->bk == P 和 P->bk->fd == P 等检查。

  8. 典型链条是 count * size 溢出回绕，malloc 申请到过小缓冲区，后续复制却按原始大 count 写入，于是形成缓冲区溢出。正确检查应在乘法前完成，例如 count <= MAX / size。

  9. %x 可能读取栈上值造成信息泄露；%s 把值当字符串指针解引用，可能任意读或崩溃；%n 把已输出长度写入指针指向位置，可能任意写并进一步劫持控制流。

  10. double free 是同一内存释放两次；use-after-free 是释放后继续使用悬空指针。联系是二者都来自对象生命周期和指针所有权错误，double free 可看作释放重引用问题的特例。

  11. SQL 注入流程包括寻找入口、测试注入、推断表和字段、获取敏感数据。数字型参数可直接拼接 and 1=1/and 1=2 测试；字符型参数需要先闭合引号再构造条件。

  12. 防御包括参数化查询、输入白名单、最小权限、错误信息收敛、日志监控。参数化查询优于关键词过滤，因为它让 SQL 结构先固定，用户输入只作为字面值绑定；关键词过滤容易被编码、注释、大小写、拼接等绕过。

  13. Heartbleed 是数组越界读/长度校验缺失漏洞。根因是处理 heartbeat 时信任报文声明长度，没有检查实际包长度是否合法，导致读取并返回超出边界的内存。

  14. 存储型 XSS 把恶意脚本存入服务器，其他用户访问时触发；反射型 XSS 通过请求参数即时反射到响应；DOM 型 XSS 由客户端脚本不安全操作 DOM 触发，不一定依赖服务器返回脚本。

  15. CSRF 流程是用户登录目标站点后访问攻击者页面，攻击者页面诱导浏览器向目标站点发请求，浏览器自动携带 Cookie，目标站点误认为用户操作。防御包括 CSRF token、SameSite Cookie、Origin/Referer 校验、敏感操作二次确认、禁止 GET 执行副作用操作。

  16. ret2libc 通常把返回地址改到已有库函数，并在栈上布置参数；ROP 则寻找大量以 ret 结尾的 gadget，并用栈上地址序列拼接出更复杂逻辑。ROP 表达能力更强，也更依赖 gadget 搜索和地址信息。

  17. ASLR 随机化代码、库、堆、栈等区域基址，使攻击者难以预测地址。粗粒度 ASLR 只改区域基址，不改模块内偏移；32 位随机熵有限；泄露一个代码指针后，可根据相对偏移推算其他地址，所以信息泄露会削弱 ASLR。

  18. Fuzzing 是自动生成或变异畸形输入，送入目标程序并监控异常的漏洞发现方法。流程是识别目标、识别输入、生成用例、执行、监控异常、保存用例、复现分析。优点是自动化、误报少、能发现真实漏洞；局限是不能证明没有漏洞，效果依赖覆盖率、样本和生成策略。

19.3 综合题答案

  1. 漏洞成因是用户输入直接拼接到 SQL，输入可改变 WHERE 条件语法树。攻击思路是闭合字符串，加入恒真条件或注释后续密码条件，使认证逻辑失效。后果包括越权登录、数据泄露、篡改和删除。防御是参数化查询、输入白名单、最小权限、关闭详细错误回显和审计日志。

  2. XSS Fuzzing 流程：先找输入点，如搜索框和 URL 参数；提交随机无害字符串，检查是否回显以及回显上下文；根据 HTML 文本、属性、事件、脚本字符串等上下文生成 payload；提交并观察是否执行；若被过滤，调整编码、闭合方式和上下文逃逸方式。先用随机字符串是为了避免 payload 被 WAF 拦截造成误判。防御是上下文输出编码、sanitizer、CSP、HttpOnly/SameSite Cookie 和安全 DOM API。

  3. 协议 Fuzz 方案：采集合法报文，聚类同类报文，识别固定字段、长度字段、类型字段、校验字段和可变域；基于模板变异边界长度、极端数值、缺失字段、重复字段和非法类型；自动发送给服务端并监控崩溃、超时、异常日志和内存错误。可能发现整数溢出、缓冲区溢出、数组越界、格式化字符串、拒绝服务和状态机错误。

  4. 第一次释放后 chunk 进入空闲链表；第二次释放同一 chunk 会让链表中出现重复引用或自引用关系。之后一次 malloc 虽然把 chunk 返回给用户，但链表状态可能仍保留对它的引用；用户写入该 chunk 的数据会覆盖空闲 chunk 原本的链表指针位置。后续 malloc/free 再解释这些位置时，会把用户数据当地址或链表指针，导致重复分配或任意写条件。

  5. DEP 使栈/堆等数据区不可执行，传统 shellcode 注入受阻，所以攻击者转向 ret2libc/ROP 等代码重用攻击，执行已有代码而不是数据区代码。ASLR 随机化地址，使 gadget 和库函数地址难以预测，提高 ROP 构造难度。但 ASLR 会被信息泄露、低随机熵、暴力尝试、模块内相对偏移不变、长时间运行进程布局稳定等因素削弱。

  6. printf(user_input); 把用户输入作为格式字符串解析。攻击者输入 %x 可泄露栈数据，%s 可造成任意读或崩溃，%n 可造成任意写。修复为 printf("%s", user_input);，并开启编译器格式检查，避免任何用户输入控制 format 参数。

  7. 风险是 count * 16 若发生整数溢出，申请的缓冲区小于实际需要，而循环仍按原始 count 写入，造成缓冲区溢出。检查方式是在乘法前判断 count <= SIZE_MAX / 16，并限制 count 的协议合法范围；也可使用编译器内建溢出检测函数。

  8. 存在 CSRF 风险。用户登录后浏览器会自动携带 Cookie，攻击者可诱导用户访问恶意页面或链接触发“取消会员”接口。防御是不要用 GET 执行副作用操作；使用 CSRF token；设置 SameSite Cookie；校验 Origin/Referer；高风险操作二次确认。
